# Raw imported C struct fields/constants are invisible to bulk symbol-graph extraction

## 1. Context

Continuing from `docs/task-own-module-declaration-gaps.md`'s §5 baseline (real `Project Iris`
corpus, 65% of cross-isolation edges unresolved): bucketing the remaining `isUnknown` edges by
`calleeUSR`/`callerUSR` shape showed one cluster dwarfing everything else found so far --
`CGSize`/`CGRect`/`CGPoint`/`UIEdgeInsets` field access and `UIControlState`/`UIControlEvents`
case constants (`.width`, `.height`, `.origin`, `.top`, `.disabled`, ...), well over a thousand
edge-endpoint mentions across the corpus.

## 2. Root-caused: these USRs never appear in `symbolgraph-extract`'s own output at all

Confirmed directly, not guessed: ran `swift symbolgraph-extract -module-name CoreGraphics` against
the real SDK and searched the output for `CGSize`. Result: `CGSize`'s own type-level USR and its
`width`/`height` field accessors appear **nowhere** in either `CoreGraphics.symbols.json` or
`CoreGraphics@CoreFoundation.symbols.json`. Genuine Swift-authored extension members on the exact
same type (`CGSize.applying(_:)`, `CGSize.equalTo(_:)`, the static `.zero`) *do* appear normally.

The distinction: `swift symbolgraph-extract` only enumerates genuinely Swift-visible API surface.
`CGSize` itself is a plain C struct (`struct CGSize { CGFloat width; CGFloat height; }`) imported
directly from a Clang header -- its own fields are synthesized wrapper accessors around raw C
storage, generated by the Swift importer at compile time, never "declared" as Swift API the
extraction tool's own model has any entry for. This is invisible to bulk extraction the exact same
way a compiler-synthesized `rawValue` getter is invisible to `SyntaxAnalysis.DeclarationExtractor`
(see `docs/task-own-module-declaration-gaps.md` §2) -- same underlying shape (a real, structurally-
guaranteed fact with literally no physical/extractable declaration anywhere), different mechanism.

`BulkSymbolGraphExtractor`'s bulk cache has no entry for these USRs at all (not even an incorrect
one), so every access anywhere in the project fell through to the live oracle path, and from there
to `unknown` for whatever the live query's own reason (a compiler-arguments issue for that
particular call site, a hover mismatch on a bridged C-struct field access, or similar -- not
investigated further, since the fix below removes the need for a live query entirely).

## 3. Why this is never actually ambiguous

A field of a plain imported C struct is categorically outside Swift's attribute system for its own
*original* declaration -- there is no possible world where `CGSize.width` carries `@MainActor`.
Swift concurrency isolation attributes only ever apply to genuinely Swift-declared or Swift-extended
API surface; a raw C struct field, synthesized by the importer, was never eligible to carry one in
the first place. This is a stronger, more general fact than "confirmed nonisolated because no
attribute was found on this particular declaration" (`SymbolGraphIsolationParser`'s own existing
default) -- it doesn't depend on absence of evidence, it's a structural guarantee.

## 4. Fix

New `Sources/IsolationCore/ImportedStructMemberMatching.swift`. Real USR mangling grammar (confirmed
against every field of `CGSize`/`CGRect`/`CGPoint`/`UIEdgeInsets` and every static case of
`UIControlState`/`UIControlEvents` observed on the real corpus):

```
s:So<N><TypeName>V<N2><MemberName><ReturnTypeMangling>vg   // instance getter
s:So<N><TypeName>V<N2><MemberName><ReturnTypeMangling>vs   // instance setter
s:So<N><TypeName>V<N2><MemberName>ABvgZ                    // static getter (.zero, .disabled, ...)
```

The discriminator against a genuine Swift-authored extension member on the same imported type
(`CGSize.applying(_:)`, mangled `s:So6CGSizeV12CoreGraphicsE8applying...`) is the presence of a
`<M><ModuleName>E` component immediately after the type name's own `V` marker -- a raw struct field
has no such component, going directly from `V` into its own length-prefixed member name.
`containerUSR(forPossibleMemberUSR:)` returns `nil` whenever that marker is present, or the shape
doesn't match at all.

Wired into `ExternalIsolationBackfill.collectEdgeLevelWorkItems` as a pre-filter, the same shape as
`SynthesizedEnumAccessorMatching` -- unlike that fix, no `linked.declarations` membership check is
needed here: the grammar match itself is sufficient proof (§3), since the type being external/SDK
means there's nothing project-local to cross-check against, and the structural guarantee holds
regardless of which specific imported struct is involved.

6 new unit tests (`ImportedStructMemberMatchingTests.swift`, including a dedicated rejection test
for the genuine-extension-member confusable shape) + 1 end-to-end test in
`ExternalIsolationBackfillTests.swift` asserting `sourceKitD.callCount == 0`.

## 5. Real `Project Iris` corpus, before/after

| | before | after |
|---|---|---|
| External oracle unknown | 2008 | **1827** (**-181**) |
| Cross-isolation edges (denominator) | 4369 | **2423** (**-1946**) |
| Unresolved % | 65% | **38%** (**-27pp**) |

By far the largest single jump in the whole `isUnknown`-reduction investigation. The denominator
itself shrinking by ~2000 (not just the numerator) confirms most of these were previously being
counted as genuine cross-isolation *boundaries* at all -- once the callee resolves cheaply to
`.nonisolated`, a `MainActor -> nonisolated` call is safe by construction and drops out of the risky-
edges list entirely, exactly like `docs/task-bulk-extraction-wrong-platform.md` §8's own phantom-
setter fix.
